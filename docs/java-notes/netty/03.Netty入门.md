## 1. Reactor 模式

Reactor 模式是网络编程里最经典的事件驱动设计模式，Netty、Redis、Nginx、Tomcat 里都能看到它。它的核心思想可以用三步概括：

> 注册感兴趣的事件 → 扫描是否有感兴趣的事件发生 → 事件发生后做出相应的处理。

### 1.1 核心思想

对照 `NioSelectorServer` 的代码，这三步的对应关系非常直接：

| Reactor 三步       | NIO 里的实现                                          |
| :----------------- | :---------------------------------------------------- |
| 注册感兴趣的事件   | `channel.register(selector, SelectionKey.OP_READ)`    |
| 扫描是否有事件发生 | `selector.select()`，阻塞等待，由内核通知就绪事件     |
| 事件发生后处理     | 遍历 `selectedKeys()`，按事件类型分发到对应的处理逻辑 |

其中 Selector 负责「扫描」，`register` 负责「注册」，「分发」由应用代码完成。把这套流程抽象出来就是 Reactor 模式。接下来用 Doug Lea《Scalable IO in Java》里的四张图，看这套模式怎么从最朴素的形态一步步演进到主从 Reactor；先说明一下图里反复出现的那些名词。

### 1.2 图里的名词说明

四张图中间都横着一排 `read → decode → compute → encode → send`，这是一条连接处理一个请求的完整流程。四张图的差别，本质就是这五步分别放在哪个线程里执行。

| 名词 | 作用 | 属于 |
| :--- | :--- | :--- |
| client | 客户端，发起连接请求的一方；图上画多个，代表并发连接的规模 | 角色 |
| Server | 服务端，监听端口、接受连接的一方 | 角色 |
| Reactor | 事件循环本体，内部持有一个 Selector，只负责「等事件」和「分事件」 | 角色 |
| dispatch | 事件分发。Reactor 拿到就绪事件后，按事件类型（accept、read、write）投给对应的处理逻辑 | 角色 |
| acceptor | 专门处理 accept 的角色，负责接下新连接并把它注册到 Reactor；在 Netty 里对应 `ServerBootstrap$ServerBootstrapAcceptor`，挂在 boss 线程上 | 角色 |
| handler | 一条连接从 read 到 send 的完整处理链；这也是 Netty 里 ChannelHandler + ChannelPipeline 的原型 | 角色 |
| Thread Pool | 业务线程池。decode / compute / encode 太重、不适合放在 Reactor 线程里做时，就丢给它执行 | 角色 |
| worker threads | 线程池里的工作线程，真正跑 decode / compute / encode 的线程 | 角色 |
| queued tasks | 任务队列。worker 线程都忙的时候，新提交的任务先在这里排队等着 | 角色 |
| mainReactor | 主 Reactor，只负责 accept | 角色 |
| subReactor | 从 Reactor，负责已建立连接的 read / send；和 mainReactor 各自独立，互不拖累 | 角色 |
| read | 从 socket 读数据，把内核接收缓冲区里的字节拷进用户态；对应上一篇「IO模型」里 NIO 的 `socketChannel.read(byteBuffer)` | IO 步骤 |
| send | 把数据写回 socket；对应 `socketChannel.write(byteBuffer)` | IO 步骤 |
| decode | 解码。网络上流动的是字节，业务要的是消息对象，这一步按协议把字节还原成消息，顺带处理粘包半包 | 业务步骤 |
| compute | 业务计算。真正干活的逻辑，比如查库、算价、拼响应，通常是整条链上最耗时的一步 | 业务步骤 |
| encode | 编码，decode 的逆操作，把业务对象按协议序列化成字节 | 业务步骤 |

`read` / `send` 是 IO 步骤，必须贴着 socket 做，天然属于持有 Selector 的那个线程；`decode` / `compute` / `encode` 是业务步骤，可以搬到别的线程去。后面四张图看的，就是这三步被搬到了哪里，以及为什么值得搬。

### 1.3 经典服务设计：一连接一线程

![Netty入门-Classic Service Designs](https://juzicoding.com/img/2026/01M4J5TEWXR9WVCS2VRENQVT75.webp)

Server 每接受一个连接就分配一个 handler 线程，线程里 read → decode → compute → encode → send 串行走完，一个请求处理完再处理下一个。这就是上一篇「IO模型」里 BIO 一连接一线程的模型图。

问题在于线程数跟连接数绑死了：连接闲着的时候，处理它的线程只能跟着等；再加上线程栈和上下文切换的开销，连接一多，服务端就撑不住。所以接下来的问题就变成了——怎么用少量线程盯住大量连接。

### 1.4 单 Reactor 单线程

![Netty入门-Basic Reactor Design](https://juzicoding.com/img/2026/01M4J5SCWV41E0R80FX1MCSWP0.webp)

一个 Reactor 线程用 Selector 监听所有连接：acceptor 只负责 accept，把新连接注册到 Reactor；连接上有事件就绪时，dispatch 把它分发给对应的 read / send；read 之后的 decode / compute / encode 也在同一个 Reactor 线程里做完，最后 send 回去。

好处是整个服务只有一个线程在跑，没有多线程竞争，实现最简单。Redis 就是这种模型，Redis 6 之后网络 IO 引入了多线程，但核心命令处理仍然是单线程。

缺点是 decode / compute / encode 属于业务步骤，一旦耗时就会卡住事件循环——这期间 accept 和其他连接的读写都只能排队等着。

### 1.5 单 Reactor 多线程

![Netty入门-Worker Thread Pools](https://juzicoding.com/img/2026/01M4J5V06J440QZD9GJQWYVZ8F.webp)

既然卡住的根源是「业务步骤和 IO 步骤挤在同一个线程里」，那就把它们分开：把 decode / compute / encode 从 Reactor 线程挪进 Thread Pool，交给 worker threads 执行；线程池忙不过来时，任务先放进 queued tasks 排队。Reactor 线程只保留 read / send，于是它能一直快速地转下去，新到的事件不会因为某个业务慢而被积压。

代价是引入了新的复杂度：线程池大小、队列积压和拒绝策略都要考虑；另外同一个连接的多个处理任务如果并行执行，返回顺序可能会乱，需要按连接保证顺序。

### 1.6 主从 Reactor 多线程

![Netty入门-Using Multiple Reactors](https://juzicoding.com/img/2026/01M4J5VCR305BYBBSS5TEMJEJ9.webp)

上一个模型里，accept 和成千上万条连接的读写仍然挤在同一个 Reactor 线程上，建连高峰会拖慢已有连接的读写。于是再拆一层：mainReactor 只负责 accept，拿到连接后注册到 subReactor；subReactor 负责 read / send 的分发；decode / compute / encode 依旧交给 worker threads 和 queued tasks；这样连接建立和读写就能各自独立扩展，互不拖累。

对应到 Netty：bossGroup 就是 mainReactor，workerGroup 里的一组事件循环就是 subReactor（4.1.x 叫 NioEventLoop，4.2.x 叫 SingleThreadIoEventLoop）。另外 Netty 默认连业务处理也在 worker 线程里执行，需要把业务隔离出去时，才额外挂一个业务线程池。

### 1.7 四种模型对比

| 模型 | 连接建立 accept | 读写事件 read / send | 业务处理 decode / compute / encode | 典型代表 |
| :--- | :--- | :--- | :--- | :--- |
| 经典服务设计 | 每连接一个线程 | 同一个线程 | 同一个线程 | BIO |
| 单 Reactor 单线程 | Reactor 线程 | Reactor 线程 | Reactor 线程 | Redis（6 之前） |
| 单 Reactor 多线程 | Reactor 线程 | Reactor 线程 | 线程池 | — |
| 主从 Reactor 多线程 | mainReactor | subReactor | 线程池（Netty 默认仍在 worker 线程） | Netty |

一句话总结 Reactor 的价值：它把「等待事件」和「处理事件」解耦，等待交给少量线程（甚至一个），处理可以按需扩展，从而用有限的线程支撑海量连接——这正是 Netty 高性能的根基。

## 2. Netty 使用场景

直接用 JDK 自带的 NIO 写网络程序，门槛并不低。一方面是 API 繁杂，`Selector`、`ServerSocketChannel`、`SocketChannel`、`ByteBuffer` 这一堆类得先熟悉；另一方面真正的麻烦不在 API 上，而在网络环境本身的不可靠：断线重连、网络闪断、心跳、半包读写、网络拥塞、异常流处理，NIO 一概不管，全得业务代码自己兜。

Netty 要解决的就是这两件事。它在 JDK NIO 之上做了一层封装，把那些通用又琐碎的网络处理收进框架里，业务代码只需要关心自己的逻辑；同时性能上也有优势，吞吐量更高、延迟更低、资源消耗更少，并且尽量减少不必要的数据复制。

版本方面，现在通用的是 4.x，5.x 已经废弃。4.2 的编译基线是 Java 8，本示例跑在 Java 21 上。

使用场景主要有三类：

1. **互联网行业**：分布式系统里各节点之间要远程调用，高性能的 RPC 框架是刚需，Netty 作为异步高性能的通信组件，常常被这些 RPC 框架当作底层通信设施。最典型的是 Dubbo，Dubbo 协议默认使用 Netty 作为基础通信组件，实现各进程节点之间的内部通信；RocketMQ 底层用的也是 Netty。Zookeeper、gRPC-Java、Spring WebFlux 的底层同样站着 Netty。
2. **游戏行业**：不管是手游服务端还是大型网络游戏，Java 的占比都不低。Netty 本身提供了 TCP/UDP 和 HTTP 协议栈，可以直接作为高性能基础通信组件使用。
3. **大数据领域**：Hadoop 的高性能通信和序列化组件 Avro，它的 RPC 框架默认采用 Netty 进行跨节点通信，Avro 的 Netty Service 也是在 Netty 之上二次封装的。

更多基于 Netty 的开源项目见 [Netty related projects](https://netty.io/wiki/related-projects.html)。

## 3. Netty 入门示例

先引入 Maven 依赖，示例使用 Netty 4.2.18.Final：

```xml
<dependency>
    <groupId>io.netty</groupId>
    <artifactId>netty-all</artifactId>
    <version>4.2.18.Final</version>
</dependency>
```

::: tip Netty 4.2 里 NioEventLoopGroup 已经过时

4.2 之前创建线程组的写法是 `new NioEventLoopGroup()`，4.2 开始 `NioEventLoopGroup` 和 `NioEventLoop` 都被标记为 `@Deprecated`，取而代之的是 `MultiThreadIoEventLoopGroup` 配合 `NioIoHandler.newFactory()`。这个改动把「事件循环」和「IO 实现」解耦了：线程组只负责调度和管理线程，具体用 NIO 还是 epoll，由注入的 `IoHandlerFactory` 决定。

:::

### 3.1 服务端

```java
package com.juzicoding.netty;

import io.netty.bootstrap.ServerBootstrap;
import io.netty.channel.ChannelFuture;
import io.netty.channel.ChannelInitializer;
import io.netty.channel.ChannelOption;
import io.netty.channel.EventLoopGroup;
import io.netty.channel.MultiThreadIoEventLoopGroup;
import io.netty.channel.nio.NioIoHandler;
import io.netty.channel.socket.SocketChannel;
import io.netty.channel.socket.nio.NioServerSocketChannel;

/**
 * Netty 服务端示例
 *
 * @author 橘子coding
 */
public class NettyServer {

    public static void main(String[] args) throws Exception {

        // 创建两个线程组 bossGroup 和 workerGroup，含有的子线程 NioEventLoop 的个数默认为 CPU 核数的两倍
        // bossGroup 只是处理连接请求，真正的和客户端业务处理，会交给 workerGroup 完成
        EventLoopGroup bossGroup = new MultiThreadIoEventLoopGroup(1, NioIoHandler.newFactory());
        EventLoopGroup workerGroup = new MultiThreadIoEventLoopGroup(NioIoHandler.newFactory());
        try {
            // 创建服务器端的启动对象
            ServerBootstrap bootstrap = new ServerBootstrap();
            // 使用链式编程来配置参数
            // 设置两个线程组
            bootstrap.group(bossGroup, workerGroup)
                    // 使用 NioServerSocketChannel 作为服务器的通道实现
                    .channel(NioServerSocketChannel.class)
                    // 初始化服务器连接队列大小，服务端处理客户端连接请求是顺序处理的，所以同一时间只能处理一个客户端连接
                    // 多个客户端同时来的时候，服务端将不能处理的客户端连接请求放在队列中等待处理
                    .option(ChannelOption.SO_BACKLOG, 1024)
                    // 创建通道初始化对象，设置初始化参数
                    .childHandler(new ChannelInitializer<SocketChannel>() {

                        @Override
                        protected void initChannel(SocketChannel ch) throws Exception {
                            // 对 workerGroup 的 SocketChannel 设置处理器
                            ch.pipeline().addLast(new NettyServerHandler());
                        }
                    });
            System.out.println("netty server start。。");
            // 绑定一个端口并且同步，生成了一个 ChannelFuture 异步对象，通过 isDone() 等方法可以判断异步事件的执行情况
            // 启动服务器（并绑定端口），bind 是异步操作，sync 方法是等待异步操作执行完毕
            ChannelFuture cf = bootstrap.bind(9000).sync();
            // 给 cf 注册监听器，监听我们关心的事件
            /* cf.addListener(new ChannelFutureListener() {
                @Override
                public void operationComplete(ChannelFuture future) throws Exception {
                    if (cf.isSuccess()) {
                        System.out.println("监听端口9000成功");
                    } else {
                        System.out.println("监听端口9000失败");
                    }
                }
            }); */
            // 对通道关闭进行监听，closeFuture 是异步操作，监听通道关闭
            // 通过 sync 方法同步等待通道关闭处理完毕，这里会阻塞等待通道关闭完成
            cf.channel().closeFuture().sync();
        } finally {
            bossGroup.shutdownGracefully();
            workerGroup.shutdownGracefully();
        }
    }
}
```

几处值得留意的地方：

- `MultiThreadIoEventLoopGroup(1, ...)` 里的 1 表示 bossGroup 只用一个线程，它只负责接收连接；workerGroup 不指定线程数，默认是 CPU 核数的 2 倍，真正的读写和业务处理都交给它。
- `.option(ChannelOption.SO_BACKLOG, 1024)` 设置的是服务端连接队列的大小。服务端处理连接请求是顺序的，同一时间只能处理一个，来不及处理的连接请求会先放进队列等待。
- `.childHandler(...)` 作用于 workerGroup 上的 SocketChannel；`.handler(...)` 作用于 bossGroup 的 ServerSocketChannel，这里没有用到。
- `bind()` 是异步的，`sync()` 只是在这里等绑定完成；后面的 `closeFuture().sync()` 会阻塞主线程，直到通道关闭。

自定义服务端 Handler：

```java
package com.juzicoding.netty;

import io.netty.buffer.ByteBuf;
import io.netty.buffer.Unpooled;
import io.netty.channel.ChannelHandlerContext;
import io.netty.channel.ChannelInboundHandlerAdapter;
import io.netty.util.CharsetUtil;

/**
 * 自定义 Handler 需要继承 netty 规定好的某个 HandlerAdapter（规范）
 *
 * @author 橘子coding
 */
public class NettyServerHandler extends ChannelInboundHandlerAdapter {

    /**
     * 读取客户端发送的数据
     *
     * @param ctx 上下文对象，含有通道 channel，管道 pipeline
     * @param msg 就是客户端发送的数据
     * @throws Exception
     */
    @Override
    public void channelRead(ChannelHandlerContext ctx, Object msg) throws Exception {
        System.out.println("服务器读取线程 " + Thread.currentThread().getName());
        // Channel channel = ctx.channel();
        // 本质是一个双向链接，出站入站
        // ChannelPipeline pipeline = ctx.pipeline();
        // 将 msg 转成一个 ByteBuf，类似 NIO 的 ByteBuffer
        ByteBuf buf = (ByteBuf) msg;
        System.out.println("客户端发送消息是:" + buf.toString(CharsetUtil.UTF_8));
    }

    /**
     * 数据读取完毕处理方法
     *
     * @param ctx
     * @throws Exception
     */
    @Override
    public void channelReadComplete(ChannelHandlerContext ctx) throws Exception {
        ByteBuf buf = Unpooled.copiedBuffer("HelloClient", CharsetUtil.UTF_8);
        ctx.writeAndFlush(buf);
    }

    /**
     * 处理异常，一般是需要关闭通道
     *
     * @param ctx
     * @param cause
     * @throws Exception
     */
    @Override
    public void exceptionCaught(ChannelHandlerContext ctx, Throwable cause) throws Exception {
        ctx.close();
    }
}
```

`channelRead` 里的 `msg` 就是客户端发来的数据，这里直接强转成 ByteBuf；`channelReadComplete` 在一次读取完成后触发，用它把 `HelloClient` 回写给客户端；`exceptionCaught` 处理异常，一般是直接关掉通道。

### 3.2 客户端

```java
package com.juzicoding.netty;

import io.netty.bootstrap.Bootstrap;
import io.netty.channel.ChannelFuture;
import io.netty.channel.ChannelInitializer;
import io.netty.channel.EventLoopGroup;
import io.netty.channel.MultiThreadIoEventLoopGroup;
import io.netty.channel.nio.NioIoHandler;
import io.netty.channel.socket.SocketChannel;
import io.netty.channel.socket.nio.NioSocketChannel;

/**
 * Netty 客户端示例
 *
 * @author 橘子coding
 */
public class NettyClient {
    public static void main(String[] args) throws Exception {
        // 客户端需要一个事件循环组
        EventLoopGroup group = new MultiThreadIoEventLoopGroup(NioIoHandler.newFactory());
        try {
            // 创建客户端启动对象
            // 注意客户端使用的不是 ServerBootstrap 而是 Bootstrap
            Bootstrap bootstrap = new Bootstrap();
            // 设置相关参数
            // 设置线程组
            bootstrap.group(group)
                    // 使用 NioSocketChannel 作为客户端的通道实现
                    .channel(NioSocketChannel.class)
                    .handler(new ChannelInitializer<SocketChannel>() {
                        @Override
                        protected void initChannel(SocketChannel channel) throws Exception {
                            // 加入处理器
                            channel.pipeline().addLast(new NettyClientHandler());
                        }
                    });
            System.out.println("netty client start");
            // 启动客户端去连接服务器端
            ChannelFuture channelFuture = bootstrap.connect("127.0.0.1", 9000).sync();
            // 对关闭通道进行监听
            channelFuture.channel().closeFuture().sync();
        } finally {
            group.shutdownGracefully();
        }
    }
}
```

客户端用的是 `Bootstrap` 而不是 `ServerBootstrap`，通道实现也换成了 `NioSocketChannel`。

自定义客户端 Handler：

```java
package com.juzicoding.netty;

import io.netty.buffer.ByteBuf;
import io.netty.buffer.Unpooled;
import io.netty.channel.ChannelHandlerContext;
import io.netty.channel.ChannelInboundHandlerAdapter;
import io.netty.util.CharsetUtil;

/**
 * 自定义客户端 Handler
 *
 * @author 橘子coding
 */
public class NettyClientHandler extends ChannelInboundHandlerAdapter {

    /**
     * 当客户端连接服务器完成就会触发该方法
     *
     * @param ctx
     * @throws Exception
     */
    @Override
    public void channelActive(ChannelHandlerContext ctx) throws Exception {
        ByteBuf buf = Unpooled.copiedBuffer("HelloServer", CharsetUtil.UTF_8);
        ctx.writeAndFlush(buf);
    }

    // 当通道有读取事件时会触发，即服务端发送数据给客户端
    @Override
    public void channelRead(ChannelHandlerContext ctx, Object msg) throws Exception {
        ByteBuf buf = (ByteBuf) msg;
        System.out.println("收到服务端的消息:" + buf.toString(CharsetUtil.UTF_8));
        System.out.println("服务端的地址： " + ctx.channel().remoteAddress());
    }

    @Override
    public void exceptionCaught(ChannelHandlerContext ctx, Throwable cause) throws Exception {
        cause.printStackTrace();
        ctx.close();
    }
}
```

`channelActive` 在连接建立完成后触发，用它发出 `HelloServer`；`channelRead` 处理服务端返回的数据。

先启动 `NettyServer`，再启动 `NettyClient`，服务端输出：

```text
netty server start。。
服务器读取线程 multiThreadIoEventLoopGroup-3-1
客户端发送消息是:HelloServer
```

客户端输出：

```text
netty client start
收到服务端的消息:HelloClient
服务端的地址： /127.0.0.1:9000
```

这里的 `multiThreadIoEventLoopGroup-3-1` 就是 workerGroup 里干活的线程，也说明 read 事件确实交给了 Worker 处理，而不是 Boss。另外要注意，客户端的 `closeFuture().sync()` 会一直等下去，示例里的连接不会主动关闭，所以跑完客户端进程不会退出，需要手动停。

看完这段代码会发现，Netty 的目标就是把业务逻辑从网络基础处理里剥出来：连接的建立、事件的监听与分发、读写的调度都由框架完成，业务只需要在 Handler 里关心「收到什么、回什么」，不用再写一大堆类似 NIO 的网络处理代码。

## 4. Netty 线程模型

Netty 的线程模型建立在《Scalable IO in Java》里那套 IO 处理模式之上。从 4.1.x 到 4.2.x，BossGroup / WorkerGroup 的划分、事件循环的循环步骤、pipeline 的走向都没有变，变的是事件循环这一层的类名和职责划分，两张图对照着看最清楚。

### 4.1 Netty 4.1.x 的 Reactor 结构

![Netty入门-Netty4.1.x Reactor工作架构图](https://juzicoding.com/img/2026/01M4JCT880V398F4V4FJFR7WH0.webp)

对照这张图：

1. Netty 抽象出两组线程池 BossGroup 和 WorkerGroup：BossGroup 专门负责接收客户端的连接，WorkerGroup 专门负责网络的读写；
2. BossGroup 和 WorkerGroup 的类型都是 `NioEventLoopGroup`；
3. `NioEventLoopGroup` 相当于一个事件循环线程组，组里含有多个事件循环线程，每一个事件循环线程就是一个 `NioEventLoop`；
4. 每个 `NioEventLoop` 都有一个 Selector，用于监听注册在它上面的 SocketChannel 的网络通信；
5. Boss 的 `NioEventLoop` 线程内部循环执行 3 步：`select`（等待事件就绪）→ `processSelectedKeys`（处理就绪事件，这里就是 accept，拿到新连接后把 channel 注册到 Worker 的 Selector）→ `runAllTasks`（执行任务队列）；
6. Worker 的 `NioEventLoop` 线程循环执行的步骤同样是这三步，区别在于 `processSelectedKeys` 里处理的是 read / write 事件；
7. Worker 的 `NioEventLoop` 处理 NioSocketChannel 的业务时，会使用 pipeline（管道），管道中维护了很多 handler 处理器，用来处理 channel 中的数据。

这一版里事件循环和 NIO 是绑死的：`NioEventLoop` 自己持有 `Selector`，自己 `select`、自己处理就绪的 `SelectionKey`，连类名里都带着 `Nio`。

### 4.2 Netty 4.2.x 的 Reactor 结构

![Netty入门-Netty4.2.x Reactor工作架构图](https://juzicoding.com/img/2026/01M4JCTST0KYG1PFKM0YK1CSBT.webp)

4.2.x 的整体结构和 4.1.x 一模一样，只是每个事件循环从 `NioEventLoop` 换成了 `SingleThreadIoEventLoop`——类名里的 `Nio` 没了。这不是单纯改名，而是把「事件循环」和「IO 实现」拆成了两层：

| 4.1.x | 4.2.x | 变化 |
| :--- | :--- | :--- |
| `NioEventLoopGroup` | `MultiThreadIoEventLoopGroup` | 线程组不再和 NIO 绑定，创建时要传入 `IoHandlerFactory`，用 NIO 就是 `NioIoHandler.newFactory()` |
| `NioEventLoop` | `SingleThreadIoEventLoop` | 事件循环本身不再认识 NIO，也不再直接持有 Selector |
| `NioEventLoop` 里的 `Selector` | `NioIoHandler` 里的 `Selector` | select、处理就绪事件都交给 IoHandler 做 |
| `SelectionKey` | `IoRegistration` | 注册的返回值换成 `IoRegistration`，通过 `submit(IoOps)` 表达关心的事件 |

对照图上的三步，落到 4.2 的代码里其实变了样：`select` 和 `processSelectedKeys` 都发生在 `NioIoHandler.run(IoHandlerContext)` 内部，`SingleThreadIoEventLoop` 只负责跑线程、跑任务队列、调用 IoHandler：

```java
// io.netty.channel.SingleThreadIoEventLoop#run（4.2.18，省略断言）
protected void run() {
    ioHandler.initialize();
    do {
        // 内部就是 ioHandler.run(context)，4.2 里 select 和 processSelectedKeys 都在里面
        runIo();
        if (isShuttingDown()) {
            ioHandler.prepareToDestroy();
        }
        runAllTasks(maxTaskProcessingQuantumNs);
    } while (!confirmShutdown() && !canSuspend());
}
```

所以图上把 `Selector` 画在事件循环里，从「这个 Selector 服务于哪个事件循环」的角度看没问题；只是 4.2 的实现里它归 `NioIoHandler` 持有，事件循环通过 `ioHandler()` 拿到它。

`NioEventLoop` 和 `NioEventLoopGroup` 在 4.2 里并没有删掉，而是变成了 `@Deprecated` 的兼容类（`NioEventLoop extends SingleThreadIoEventLoop`、`NioEventLoopGroup extends MultiThreadIoEventLoopGroup`），老代码照样跑，新代码应该换成新 API。拆开的好处是同一套 group / loop 可以配不同的 IO 实现：Linux 上想换成 epoll，只要把工厂换成 `EpollIoHandler.newFactory()`，事件循环这一层不用动。

这也正好对上第 1 节 Reactor 模式的划分：BossGroup 就是主 Reactor，只做 accept；WorkerGroup 是从 Reactor，负责读写事件的分发；pipeline 上的业务处理最终落在 Worker 的线程上。

## 5. Netty 核心组件

**Bootstrap / ServerBootstrap**

引导类。一个 Netty 应用通常由一个 Bootstrap 开始，主要作用是配置整个 Netty 程序、把各个组件串联起来。Netty 中 `Bootstrap` 是客户端程序的启动引导类，`ServerBootstrap` 是服务端启动引导类。

**Future / ChannelFuture**

Netty 中所有的 IO 操作都是异步的，调用之后不能立刻得知消息是否被正确处理，所以这些调用都会返回一个 Future。可以过一会再等它执行完成，或者直接注册一个监听器（`addListener()`），操作成功或失败时监听器会自动触发。入门示例里的 `bootstrap.bind(9000).sync()` 和 `closeFuture().sync()` 用的就是这个机制。

**Channel**

Netty 网络通信的组件，用于执行网络 IO 操作。Channel 为用户提供：

1. 当前网络连接的通道的状态（例如是否打开、是否已连接）；
2. 网络连接的配置参数（例如接收缓冲区大小）；
3. 异步的网络 IO 操作（如建立连接、读写、绑定端口），异步意味着任何 IO 调用都将立即返回，并且不保证在调用结束时所请求的 IO 操作已经完成；
4. 调用立即返回一个 `ChannelFuture` 实例，通过往 `ChannelFuture` 上注册监听器，可以在 IO 操作成功、失败或取消时得到回调通知；
5. 支持关联 IO 操作与对应的处理程序。

不同协议、不同阻塞类型的连接都有不同的 Channel 类型与之对应，常用的有：

| Channel | 说明 |
| :--- | :--- |
| `NioSocketChannel` | 异步的客户端 TCP Socket 连接 |
| `NioServerSocketChannel` | 异步的服务器端 TCP Socket 连接 |
| `NioDatagramChannel` | 异步的 UDP 连接 |
| `NioSctpChannel` | 异步的客户端 SCTP 连接 |
| `NioSctpServerChannel` | 异步的服务器端 SCTP 连接 |

这些通道涵盖了 UDP 和 TCP 网络 IO 以及文件 IO。这些通道在这一层没有受 4.2 的影响，类名照旧。

**Selector**

Netty 基于 Selector 对象实现 IO 多路复用，通过 Selector，一个线程可以监听多个连接的 Channel 事件。向 Selector 注册 Channel 之后，Selector 内部的机制会自动不断地查询这些注册的 Channel 是否有已就绪的 IO 事件（例如可读、可写、网络连接完成等），这样一个线程就能高效地管理多个 Channel。

4.2 开始 Selector 不再由事件循环直接持有，而是交给 `NioIoHandler`，事件循环通过 IoHandler 使用它，见下一条。

**IoHandler / IoHandlerFactory**

这两个是 4.2 新抽出来的一层，用来把「事件循环」和「IO 实现」解耦：

- `IoHandler`：真正的 IO 实现，负责 select、处理就绪事件、注册 `IoHandle`，以及唤醒和销毁。NIO 对应 `NioIoHandler`（Selector 就在它内部），Linux 上的 epoll 对应 `EpollIoHandler`；
- `IoHandlerFactory`：创建 IoHandler 的工厂。线程组创建时把工厂传进去，每个事件循环启动时用它 new 一个自己的 IoHandler。

```java
// 创建线程组时注入用哪种 IO 实现
EventLoopGroup bossGroup = new MultiThreadIoEventLoopGroup(1, NioIoHandler.newFactory());
EventLoopGroup workerGroup = new MultiThreadIoEventLoopGroup(NioIoHandler.newFactory());
```

换成 epoll 只需要把 `NioIoHandler.newFactory()` 改成 `EpollIoHandler.newFactory()`。

**SingleThreadIoEventLoop**

4.1.x 里这个角色叫 `NioEventLoop`，4.2 改名为 `SingleThreadIoEventLoop`：内部维护了一个线程、一个任务队列和一个 `IoHandler`，支持异步提交执行任务。线程启动时会调用 `run` 方法，循环处理两类任务：

- IO 处理：`runIo()`，内部就是 `ioHandler.run(context)`，也就是 4.1.x 里的 `select` + `processSelectedKeys`，就绪事件 accept、connect、read、write 都在这一步处理；
- 非 IO 任务：`runAllTasks()`，处理添加到 taskQueue 中的任务，如 register0、bind0。

**MultiThreadIoEventLoopGroup**

4.1.x 里这个角色叫 `NioEventLoopGroup`，4.2 改名为 `MultiThreadIoEventLoopGroup`：主要管理 eventLoop 的生命周期，可以理解为一个线程池，内部维护了一组线程，每个线程（`SingleThreadIoEventLoop`）负责处理多个 Channel 上的事件，而一个 Channel 只对应于一个线程。

::: tip Channel 和线程是绑定的

一个 Channel 上的事件永远由同一个线程处理，所以 Handler 里不用为共享状态加锁；反过来，Handler 里只要有一个阻塞操作，就会卡住这个线程上其他所有 Channel 的事件。

:::

**ChannelHandler**

`ChannelHandler` 是一个接口，处理 IO 事件或拦截 IO 操作，并将其转发到其 ChannelPipeline（业务处理链）中的下一个处理程序。

这个接口本身有很多方法需要实现，直接实现不方便，所以通常继承它的子类：

```text
ChannelInboundHandler    用于处理入站 IO 事件
ChannelOutboundHandler   用于处理出站 IO 操作
```

或者使用适配器类：

```text
ChannelInboundHandlerAdapter    用于处理入站 IO 事件
ChannelOutboundHandlerAdapter   用于处理出站 IO 操作
```

**ChannelHandlerContext**

保存 Channel 相关的所有上下文信息，同时关联一个 `ChannelHandler` 对象。

**ChannelPipeline**

`ChannelPipeline` 保存 `ChannelHandler` 的 List，用于处理或拦截 Channel 的入站事件和出站操作。

`ChannelPipeline` 实现了一种高级形式的拦截过滤器模式，使用户可以完全控制事件的处理方式，以及各个 `ChannelHandler` 之间如何相互交互。在 Netty 中，每个 Channel 都有且仅有一个 `ChannelPipeline` 与之对应：

![Netty入门-ChannelPipeline 结构](https://juzicoding.com/img/2026/01M4JF7B212Z1PNA7WDN4Z9QSS.webp)

一个 Channel 包含一个 `ChannelPipeline`，而 `ChannelPipeline` 中又维护了一个由 `ChannelHandlerContext` 组成的双向链表，并且每个 `ChannelHandlerContext` 中又关联着一个 `ChannelHandler`。

read 事件（入站事件）和 write 事件（出站事件）走在同一个双向链表上：入站事件会从链表 head 往后传递到最后一个入站的 handler，出站事件会从链表 tail 往前传递到最前一个出站的 handler，两种类型的 handler 互不干扰。

## 6. ByteBuf

从结构上来说，ByteBuf 由一串字节数组构成，数组中每个字节用来存放信息。

ByteBuf 提供了两个索引，一个用于读取数据，一个用于写入数据，这两个索引通过在字节数组中移动，来定位需要读或者写信息的位置。当从 ByteBuf 读取时，它的 readerIndex（读索引）会根据读取的字节数递增；同样，当写 ByteBuf 时，它的 writerIndex 也会根据写入的字节数递增。

![Netty入门-ByteBuf 读写索引](https://juzicoding.com/img/2026/01M4JF7QH9JCB9496YJ3H2170B.webp)

以 `Unpooled.buffer(10)` 为例，capacity 是 10，两个索引把整个数组切成三个区域：

| 区域 | 范围 | 说明 |
| :--- | :--- | :--- |
| 已读区域 | `[0, readerIndex)` | 已经读过的字节，想重读需要手动把 readerIndex 移回去 |
| 可读区域 | `[readerIndex, writerIndex)` | `readableBytes()` 的大小，也是 `readXxx()` 真正能读到的部分 |
| 可写区域 | `[writerIndex, capacity)` | 还能写入多少字节，写满之后会自动扩容 |

需要注意的是极限的情况：readerIndex 刚好等于 writerIndex，此时没有可读数据。如果 readerIndex 超过了 writerIndex，Netty 会抛出 `IndexOutOfBoundsException`。

示例代码：

```java
package com.juzicoding.netty;

import io.netty.buffer.ByteBuf;
import io.netty.buffer.Unpooled;
import io.netty.util.CharsetUtil;

/**
 * Netty ByteBuf 示例
 *
 * @author 橘子coding
 */
public class NettyByteBuf {
    public static void main(String[] args) {
        // 创建 byteBuf 对象，该对象内部包含一个字节数组 byte[10]
        // 通过 readerIndex、writerIndex、capacity 将 buffer 分成三个区域
        // 已经读取的区域：[0, readerIndex)
        // 可读取的区域：[readerIndex, writerIndex)
        // 可写的区域：[writerIndex, capacity)
        ByteBuf byteBuf = Unpooled.buffer(10);
        System.out.println("byteBuf=" + byteBuf);

        for (int i = 0; i < 8; i++) {
            byteBuf.writeByte(i);
        }
        System.out.println("byteBuf=" + byteBuf);

        for (int i = 0; i < 5; i++) {
            System.out.println(byteBuf.getByte(i));
        }
        System.out.println("byteBuf=" + byteBuf);

        for (int i = 0; i < 5; i++) {
            System.out.println(byteBuf.readByte());
        }
        System.out.println("byteBuf=" + byteBuf);


        // 用 Unpooled 工具类创建 ByteBuf
        ByteBuf byteBuf2 = Unpooled.copiedBuffer("hello,juzicoding!", CharsetUtil.UTF_8);
        // 使用相关的方法
        if (byteBuf2.hasArray()) {
            byte[] content = byteBuf2.array();
            // 将 content 转成字符串
            System.out.println(new String(content, CharsetUtil.UTF_8));
            System.out.println("byteBuf2=" + byteBuf2);

            // 获取数组 0 这个位置的字符 h 的 ASCII 码，h=104
            System.out.println(byteBuf2.getByte(0));

            // 可读的字节数：17
            int len = byteBuf2.readableBytes();
            System.out.println("len=" + len);

            // 使用 for 循环取出各个字节
            for (int i = 0; i < len; i++) {
                System.out.println((char) byteBuf2.getByte(i));
            }

            // 范围读取
            System.out.println(byteBuf2.getCharSequence(0, 6, CharsetUtil.UTF_8));
            System.out.println(byteBuf2.getCharSequence(6, 11, CharsetUtil.UTF_8));
        }
    }
}
```

两次连续的 0 到 4 值得对比一下：第一次是 `getByte(i)` 随机读，readerIndex 一直是 0；第二次是 `readByte()` 顺序读，读完 readerIndex 变成了 5。这就是 `getXxx()` 和 `readXxx()` 的区别——前者只按索引取值，不改变读索引，后者读完会推进读索引。

最后和 JDK 的 `ByteBuffer` 对比一下：`ByteBuffer` 只有一个 position，读完想写、写完想读，都得先 `flip()` 或 `clear()` 切换模式；ByteBuf 把读索引和写索引分开，读写互不干扰，也就不需要翻转这一步。此外 ByteBuf 的容量可以按需自动扩容，还支持池化复用，这些都是它比 `ByteBuffer` 更顺手的地方。
